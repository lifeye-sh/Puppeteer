# 后端功能模块开发规划

前端逐轮接入采用 [R00–R17 迁移执行计划](frontend-migration-plan.md)。W0–W4用于模块基础建设，R轮次用于真实前端验收；每轮需同时交付后端、前端适配、部署与验证记录，完整范围按[执行卡](migration-rounds.md)收口。

本轮实施细化见 [D01–D07 可落地实施决策](implementation-decisions.md)：5 份协议/运维规范、15 个开发任务和 103 个属性定义。模块划分保持不变，各任务卡已关联对应实施规范；先完成 W0 配置与能力底座，再按前置顺序开发真实业务闭环。

本规划将后端重组为 **18 个业务模块 + 1 套公共基础设施**。每个模块拥有自己的业务规则、数据写入口、公开契约和验收条件，可以单独分配开发任务。部署仍采用 Go 模块化单体控制面、Connector 和 Worker，不要求每个功能模块运行成独立微服务。

本规划是当前模块边界与开发顺序的依据。原架构、业务流程和接口文档保留为详细设计；涉及数据归属或代码目录冲突时，以本规划和 [模块目录 JSON](module-catalog.json) 为准。模块卡描述全量目标；R01 已交付 F00/M01/M08/M18 的最小切片，实际边界见 [后端运行说明](../../backend/README.md)，不能据此将整个模块标为完成。

使用文档核对后新增 36 项需求，分别登记主责、协作、阶段和验收。详见[修订说明](usage-docs-review.md)、[全量覆盖矩阵](usage-coverage.md)和[系统属性目录](system-property-catalog.md)。原生 RDP、Termark、官方备份格式互通不得仅因出现界面入口便标记已支持；发布前须通过专项验收。

## 相比原服务划分的调整

| 原划分 | 新归属与原因 |
|---|---|
| Identity 与 Federation | 合为 M01，外部身份作为内部子包；统一账号与认证生命周期 |
| Identity 中的角色关系 | 移到 M02；users 属于 M01，roles/user_roles/permissions 属于 M02 |
| AssetCatalog 同时拥有全部资源配置 | M03 拥有注册表和主机；网站配置由 M09、数据库配置由 M10 拥有 |
| Secret 与 Automation 中的轮换 | 全部轮换规则与状态归 M04；M12 只负责触发 |
| Session 与 Audit 的录像边界 | sessions 归 M06，recordings 与全部审计日志归 M08 |
| Filesystem 中的 snippets | 移到 M12；文件浏览与脚本复用分开 |
| Operations 包含大量不同业务 | 拆为 M15 监控诊断、M16 备份恢复、M18 配置；IP 集和 GeoData 归 M02 |
| 用户客户端证书 | 元数据与签发吊销归 M13；账户页面通过应用流程调用 |
| Approval 和 DatabaseProxy 共管工单执行 | 工单与执行记录归 M11，SQL 执行能力归 M10，应用流程协调两者 |
| 所有任务都写在 Worker | Worker 是运行容器；任务业务处理器归各模块，队列机制归 F00 |

表归属指业务代码的唯一写入所有者。模块间保留真实外键；共享 PostgreSQL 并不意味着可以绕过模块访问其表。新增的审计去重辅助表 `audit_event_receipts` 若实施，归 M08；其他新增表必须先登记所有者。

## 模块的三种边界

1. **功能边界**：一个模块拥有完整业务概念，例如轮换的准备、远程更新、验证、补偿都属于 M04，不能分散到调度和资产模块各维护一段状态。
2. **代码边界**：模块内部隐藏 domain、service、repository；外部只使用公开契约。consumer 定义所需窄接口，application 层注入适配器。
3. **运行边界**：同一模块可能在 server、connector、worker 中运行不同适配器，例如 M08 的查询在 server、录屏接收在 connector、转码在 worker。不能把“进程”与“功能模块”混为一谈。

单个 Go module 起步，不为 18 个业务包分别建 go.mod。也不采用运行时 Go plugin 加载业务；模块通过构建时注册，配置决定是否启用已实现能力。

## 推荐代码结构

```text
backend/
  cmd/{server,connector,worker,agent,migrate,nt}/
  internal/
    kernel/                     Actor、ID、错误和契约版本等少量稳定类型
    platform/                   F00
    modules/
      identity/                 M01
        module.go               组装与公开用例入口
        contracts.go            不含数据库实体的公开类型
        internal/
          domain/
          application/
          ports/                本模块需要的外部窄接口
          adapters/postgres/
          adapters/http/
        migrations/
        tests/
      authorization/ resource/ vault/ connectivity/
      session/ files/ audit/ webproxy/ database/
      approval/ automation/ pki/ notification/
      operations/ backup/ ai/ system/
    application/
      bootstrap/                注册、装配、依赖与能力检查
      workflows/                跨模块用例，按业务文件拆分
      readmodels/               只读聚合、门户、仪表盘
      compatibility/            保持旧前端 DTO/路由
  api/
    modules/<module>/openapi.yaml
    proto/
  migrations/manifest.json      各模块迁移的全局有序清单
  deploy/
```

Go 的嵌套 `internal` 限制配合 CI import 检查阻止其他模块导入私有实现。公开 facade 只导出命令、查询、结果和事件类型，不导出 Repository 或 `*pgxpool.Pool`。application 层可以组装多个模块，但不能自行写领域表或重新实现模块规则。

模块迁移存放在所属模块，manifest 使用全局递增版本，启动前由 migrate 一次执行。表名暂沿用已有逻辑模型，避免仅为目录美观批量改名；跨模块 FK 的迁移必须声明前置迁移。独立开发指契约与实现可分别验证，不承诺带依赖的模块可以在空库中单独迁移。

## 跨模块协作规则

### 身份与权限的协作

M01 解析登录会话，返回 Actor 与主体事实；M02 接收事实并做策略判定。M01 管理 API 的 HTTP adapter 在应用层装配 M02 的守卫，M02 获取组织事实时使用 M01 的只读端口。两个模块之间不直接导入彼此 service，不在 Evaluate 中递归调用受同一守卫保护的 HTTP API。

M01 与 M02 可以在同一批次分别开发，但受保护用例必须集成验证后才发布。开发顺序图不是完整运行依赖图；不能因为 `buildAfter` 没写 M02 就让身份管理接口免鉴权。所有入口默认拒绝，公开入口显式登记。

### 数据写入与原子事务

所有权规则：其他模块不能写你的表、不能拿你的 Repository、不能拼接更新你的列。跨模块事务通过 F00 UnitOfWork 和模块公开的事务内命令完成，事务上下文是受控作用域，不向调用者暴露 SQL 连接。

例如访问审批：

```text
AccessApprovalWorkflow
  1. 验证 Actor 和审批范围
  2. 开始 UnitOfWork
  3. M11 锁定申请并确认可批准
  4. M02.CreateTemporaryGrant(scope, command)
  5. M11.MarkApproved(scope, grantId)
  6. M08.AppendInTx(scope, audit)
  7. F00.Outbox.Append(scope, event)
  8. 提交；M14 在提交后处理通知
```

只锁定一个申请仍不足以处理权限并发变化；需验证批准时使用的角色/资源/策略 revision。所有涉及相同数据的流程使用一致的锁顺序。事务内禁止远程 SSH、SQL、邮件、模型 API 或对象上传。

只读聚合由 application/readmodels 完成。优先调用公开查询端口；大分页采用经过评审、明确所有者和权限条件的只读 SQL view/投影，不允许每个模块自行跨表查询。列表必须先限定授权范围再分页和计数，不能先返回全量 total 再过滤。

### 长任务与外部副作用

F00 负责队列机制，M12 负责调度时间，业务模块负责执行规则。例如：M12 触发 → F00 job → M04 的 RotationHandler → M05/M06 的连接能力 → M04 持久化轮换结果 → M08 审计/M14 通知。

每个 handler 注册 kind、payload schema、幂等键、超时、取消方式和重试分类。远程写入结果不明确时由业务报告 unknown/needs_reconcile，基础队列不能自动重放。Worker 只能运行已注册且对应能力启用的 handler。

### 事件、配置与秘密

- 事件由事实所属模块发布，包含 eventId、aggregateVersion、schemaVersion、actorRef 和 traceId；不携秘密与大对象。
- 审计要求随业务事务提交时调用 M08 的事务内端口；outbox 不能代替这条强一致审计路径。
- M18 保存设置值和 revision；每个 key 注册唯一领域所有者、schema、权限、校验器、脱敏规则及是否重启。网站设置由 M09 校验，AI 设置由 M17 校验。
- M01 拥有 user_preferences，AI/终端偏好经其命名空间端口保存，不能其他模块直接更新同一行 JSON。
- M04 提供秘密服务，F00 仅提供加密算法/密钥封装适配；任何模块都不能因可调用 Cipher 就自行绕开秘密租约和查看审计。

## 关键业务流程的模块编排

| 用例 | 应用流程与模块职责 |
|---|---|
| 初始化管理员 | M18 检查初始化状态 → M01 创建用户 → M02 建立初始角色/权限 → M08 审计 → M18 标记完成，同事务 |
| 创建网站/数据库资源 | M03 创建 registry → M09/M10 创建所属资源 → M08 审计，同事务；删除保留 registry tombstone |
| 建立 SSH 会话 | M01 Actor → M03 资产事实 → M02 决策 → M05 路径 → M06 预约/连接 → M04 秘密租约 → M08 录屏 |
| 上传文件 | M06 返回受权会话上下文 → M02 操作策略 → M07 挂载/配额/传输 → M08 文件审计 |
| 审批临时访问 | M11 范围和申请 → M02 grant → M11 批准状态 → M08 审计 → outbox → M14 通知 |
| 审批并执行 SQL | M11 冻结审批参数并入队 → M10 执行 → M11 保存 executed/failed/unknown → M08 审计 |
| 凭据轮换 | M12 定时或手动触发 → M04 轮换状态机 → M05/M06 连接适配 → M04 验证激活 → M08/M14 |
| 恢复备份 | M16 验证 → 应用维护协调器暂停新写入/任务和排空连接 → M16 恢复 → M01/M06 撤销旧能力 → 恢复验证 |
| AI 文件修改 | M17 对话与工具审批 → 应用 AuthorizedTool 重新鉴权 → M07 实际修改 → M08 审计 → M17 保存结果 |

这些流程归 `application/workflows`，不是新增一个可随意操作全库的“业务总服务”。每个流程保持单一用例、明确补偿和验收用例。

## 统一交付标准

每个模块都按以下顺序交付，不能以“已建目录”或“CRUD 可返回 200”完成：

1. **契约包**：功能范围、公开命令/查询、DTO、错误、权限、事件及版本、幂等和取消语义。
2. **数据包**：模块迁移、唯一约束/外键/索引、版本字段、保留与秘密处理规则。
3. **实现包**：领域规则、应用服务、Repository、HTTP/协议/任务 adapter，接入实际认证与授权。
4. **验证包**：模块内规则测试、真实 PostgreSQL 事务测试、前端契约测试、越权/重放/并发/失败场景。
5. **集成包**：至少一个真实跨模块用例，记录依赖版本和未开启能力，不用 mock 通过代替生产集成。
6. **运营包**：关键指标、结构化日志、审计事件、健康条件、配置说明和故障恢复步骤。

验收至少包含正常场景、未登录、无权限、无效输入、重复提交、并发修改、依赖不可用、取消/超时、重启恢复和秘密泄露检查。协议模块额外进行真实客户端验证，外部写操作测试不以安全重试为默认前提。

## 新模块与边界变更流程

新增模块先在 module-catalog.json 登记稳定 ID、职责、表、端口、事件、前端证据及验收条件，再生成任务卡。改变表归属时同时迁移 Repository、公开查询、迁移文件归属和测试；不能只修改文档标题。修改通用契约时列出受影响模块，用兼容窗口或版本化迁移处理，不让下游开发靠阅读提交记录猜变化。

执行 `node scripts/backend-module-docs.mjs` 会校验所有旧逻辑表都有且只有一个所有者、前置模块存在且无开发顺序环、源码证据文件存在，并生成独立任务卡与索引。后端代码存在后，再在 CI 增加私有包导入检查、路由所有权覆盖和迁移清单校验；当前文档校验不冒充这些尚未实施的代码规则。

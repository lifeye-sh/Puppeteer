# Puppeteer 后端设计

本方案为当前前端设计独立的 Go 与 PostgreSQL 后端，覆盖资产、身份、远程会话、审计、网站代理、数据库代理、审批、自动化和 AI 业务。采用模块化单体控制面、独立连接数据面和异步 Worker。数据库保存业务真相，连接节点持有实时连接，录屏与大文件进入独立存储。

当前按 **18 个业务模块 + F00 公共基础设施** 组织开发。优先阅读[模块开发规划](module-development-plan.md)和[模块任务索引](module-backlog.md)，各模块有独立任务卡。模块边界、代码目录、表所有权与开发批次以这份新规划为准。

设计基线：前端提交 `a43c7d83519bd9af3a80e3769f96e178aff9d29c`，日期 2026-10-26。用户已确认 Go + PostgreSQL。这里是独立后端的全量设计，不是闭源后端的还原。R16 已完成开发与本轮验证收口，R17 按全新生产部署规划推进；见 [运行说明](../../backend/README.md)、[R11 验收](acceptance/R11.md)。其他轮次以各自验收记录为准，后续轮次设计不等于已实现。

2026-10-26 已核对官方中文使用文档全部 27 篇正文与 58 处图示，以及 4 篇关联资料；嵌入视频未能读取。新增 36 项模块需求、103 个配置键目录，修正原生客户端、数据库、Web 和备份的兼容边界。先读[使用文档修订说明](usage-docs-review.md)，再按任务卡开发。

本轮已把原“尚需实施验证”补成[可落地实施决策](implementation-decisions.md)：7 个技术决策、15 个开发任务、5 份详细规范，以及 103 个属性的设计默认值/类型/校验/生效方式。核心开发采用公开标准与自有协议，私有兼容单独登记。

## 已确定的架构决策

1. 单实例组织模型起步，不把当前用户和部门机制冒充为 SaaS 租户隔离；多组织部署使用独立实例。
2. 一个 Go 仓库包含 `server`、`connector`、`worker`、`agent`、`migrate` 和运维 `nt` CLI 入口；网站和数据库代理可作为 connector 的独立运行角色部署。
3. HTTP API 保持现有 `/api` 路径和直接 JSON 返回值，不新增全局 `data` 包装。
4. 浏览器登录使用服务器会话 Cookie；API Key、分享令牌、原生客户端票据分别管理，不能互换。
5. 操作权限、资产授权、接入策略、会话能力四层统一在服务端执行。
6. PostgreSQL 负责事务、任务、outbox 和租约。首版不强制 Redis、Kafka、Elasticsearch。
7. SSH 使用 Go SSH 协议库；浏览器 RDP/VNC 经 Guacamole/guacd；原生 RDP 确定 FreeRDP 侧车，按桌面、通道策略、RemoteApp 分 profile 交付。
8. 录屏、上传、轮换、SQL 执行等外部副作用采用可恢复状态机；不承诺跨外部系统的“恰好一次”。
9. 前端许可证字段由独立产品的能力适配层承接，不能以返回成功代替实际实现或冒充官方许可证校验。
10. 功能模块与部署进程分开；模块独占数据写入口，通过公开端口和 application/workflows 协作。

## 证据与设计的区别

- **前端契约**：请求路径、参数、类型、组件读取方式和消息常量，来自本仓库。
- **官方使用行为**：来自已核对的正文与图示；跨版本冲突、视频缺口和未公开协议在修订说明中显式记录。
- **设计决策**：数据库表、模块名称、内部 RPC、授权合并规则和容量目标，由本方案定义。
- **实施与验收状态**：公开技术路径和自有协议已定义，真实客户端/恢复/故障测试随开发执行；官方私有协议兼容需要外部契约。设计完成不等于功能已实现或实测通过。

重新生成接口证据：在仓库根目录执行 `node scripts/backend-contract-inventory.mjs`。脚本使用当前锁文件中的 `@babel/parser` 进行 AST 解析；它是文档工具，不改变前端运行行为。生成清单包括继承 API 的候选方法，因此不能直接用条目数充当真实服务端接口数。

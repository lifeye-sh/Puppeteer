# 系统检查更新与自升级

状态：beta0.11 提供系统更新与自升级功能。U1 更新发现、U2 标准受管部署的管理员确认自升级，以及 U3 自动准备、受限维护窗口升级、通知、保留策略和 AI 只读查询已接通。自动安装默认关闭；管理员必须先明确授权版本上限、有效期和停机窗口。

## 开发范围

| 阶段 | 内容 | 当前状态 |
| --- | --- | --- |
| U1 更新发现 | 签名索引、渠道、版本比较、自动检查、历史、实际组件状态和兼容性检查 | 已实现，见下方验证范围 |
| U2 自升级闭环 | 独立升级进程、互斥锁、镜像准备、维护排空、备份、迁移、切换、验证和失败恢复 | 标准受管部署已实现，已通过隔离 systemd/Docker/PostgreSQL 的升级与切换中断恢复验证 |
| U3 计划与自动升级 | 自动准备、维护窗口、限期授权、通知、产物保留和 AI 只读查询 | 已实现，隔离环境验证自动准备和窗口升级 |

## 当前使用方式

管理员在“系统运维 → 系统更新”查看后端版本、数据库版本及实际运行组件。菜单与接口均限制为拥有身份管理权限的平台管理员。

“检查更新”读取项目固定 HTTPS 地址的签名发布索引，使用随应用分发的 Ed25519 公钥校验。拒绝重定向、过大响应、无效签名、未知签名密钥、过期索引、发布序号回退及同序号内容变化。网页不能传入任意下载地址、镜像或脚本。

支持 Beta 与稳定版渠道。默认每天自动检查，检查间隔可设置为 1–168 小时或关闭自动检查。自动检查只获取版本信息，不拉取镜像、不重启服务。网络请求使用服务端 HTTPS 出站代理环境设置。

状态区分未检查、检查中、发现新版本、当前渠道已是最新、当前版本高于渠道、渠道无版本、无法识别当前版本、索引过期与检查失败。网络错误不会被显示为最新版本，保留上次成功时间及最近 30 次检查记录。

检查记录和设置保存于应用数据目录的 `runtime/system-updates.json`，不新增数据库迁移。写入采用临时文件与原子替换，权限 0600；重启后重新验证缓存索引签名。管理接口使用现有授权和审计机制，设置并发修改通过 revision 拒绝覆盖。

## 兼容性检查边界

执行器读取受管 Compose 配置和实际容器状态，只返回选定组件的镜像、版本、健康与停用状态，不返回环境变量、凭据和完整配置。

检查目标版本、最低来源版本、数据库版本方向、执行器可达性、实际平台、受管布局、宿主机 systemd、部署互斥及组件健康与配置一致性。不能通过后端容器为 Linux 推断宿主机有 systemd。

页面的“升级预检”是提交前检查：通过后可确认目标版本、停机影响，并输入当前管理员密码及已绑定 MFA 的新动态口令。管理员身份、签名索引和部署快照由后端与宿主机复核，浏览器不能提交镜像、脚本或操作者身份。

预检通过不代表已完成备份。提交后先进入“准备镜像与检查空间”，通过后才排空会话和停止业务写入，制作并验证配套备份；备份验证通过才切换版本。各阶段失败均显示原因。浏览器关闭不会取消任务，刷新页面会重新查询宿主机记录。

首次启用需要按[升级说明](UPGRADE.md)通过受管脚本升级到包含本功能的发布版本，同时更新后端、执行器和独立进度配置。仅替换后端镜像不足以启用此功能。

## U2 执行设计

### 已实现的事务与冻结机制

- 宿主机事务保存到安装目录的 `config/upgrade-state/upgrade.json`，使用文件和目录同步、原子替换；记录目标、来源、操作者、部署摘要及阶段。日志不包含命令输出或凭据。
- 事务创建独立验证发布签名与升级方向，维护宿主机发布序号记录，拒绝回退和相同序号的不同内容。相同请求标识不会重复执行，已归档标识也不能复用为新升级。
- Linux 进程锁与手动升级脚本共用 `.upgrade.lock`。部署执行器的任务、预检及定时维护还检查持久化升级日志，进程退出不会使尚未恢复的实例被视为空闲。日志损坏时拒绝部署。
- 阶段覆盖准备、排空、备份、切换、验证、开放写入及成套恢复。切换或验证中断必须先关闭写入、校验备份，再调用配套恢复操作；备份前的失败恢复原服务。恢复失败保留阻塞状态。
- `committing` 和 `rollback_committing` 在开放写入前持久化。进程在此后退出，只能继续核验与激活，不能再次恢复旧备份覆盖新写入。事务层不把宿主机命令的错误输出写入进度日志。
- 后端识别只读挂载中的 `NT_UPGRADE_HOLD` 标记；标记存在、异常或不可访问时保持冻结。冻结阶段保留健康检查，关闭业务接口和后台工作。`/readyz` 返回版本、冻结状态及升级标记状态。开放时先核对数据库与密钥配置，再完成被延迟的初始化；失败继续保持冻结。
- 新安装登记升级标记路径；手动升级受管部署时同步该配置。手动升级拒绝未完成或损坏的升级记录，配置归档排除事务目录和运行时 socket 目录，防止以后恢复配置时覆盖升级记录。
- 宿主机应用控制接口限定本机回环、部署凭据和仍有效的管理员身份，拒绝浏览器来源；排空与恢复操作记录审计。排空前检查运行中的任务并占用重任务配额，暂停后台工作、关闭会话、等待请求退出；重复排空不会重复占用配额。`nt upgrade-control` 供后续固定宿主机操作调用，不能替代完整升级入口。

固定宿主机适配器位于 `backend/internal/platform/hostupgrade`，使用随执行器构建的操作代码；不下载或执行发布源提供的脚本。管理员提交后复制当前执行器到任务专属目录，启动 `puppeteer-upgrade-<项目>.service`，因此替换后端和部署执行器不会停止升级事务。执行器启动后检查持久化任务，必要时重新启动独立进程；恢复故障时只保留进度服务，不自动再次覆盖数据。

### 支持范围与预检拒绝条件

- Linux amd64、宿主机 systemd、Python 3.9 或更高版本、标准单一 `compose-managed.json` 受管安装；Docker Desktop 容器化执行器可检查版本，但不能运行此自升级流程。
- 标准内部 PostgreSQL 18，数据库与应用配置一致；不升级 PostgreSQL 大版本。拒绝外部数据库、已切换恢复数据库的运行时配置、WAL 专用部署及未知服务。
- 应用数据必须位于项目所属的本地命名卷，卷不能被其他项目引用。拒绝未知可写卷、可写宿主机绑定目录、安装目录外的绑定挂载、主机网络、特权或设备映射。
- 当前不支持启用 RDP 共享盘的布局。图形服务和 MP4 服务可保持原有启停状态；网页 RDP 本身不要求启用共享盘。
- 原组件和目标组件使用官方固定摘要镜像。目标后端必须声明冻结协议和部署格式 `v1`；不能用此流程跨越不兼容的安装布局。
- 检查业务任务、备份/恢复状态和管理员权限，检查实际运行容器与配置一致。备份空间要求至少两倍当前数据库、应用卷及配置大小，再加 1 GiB；镜像下载后和停写后再次检查。镜像层由 Docker 存储管理，拉取空间不足时在停写前退出。
- 备份不接受符号链接、硬链接、设备或越界归档路径，校验失败不会进入版本切换。

`runnerReady` 仅表示宿主机启动能力和进度入口已接入；完整布局、空间及备份校验在独立任务中执行，不能把该字段视作整个升级已通过。

### 备份、恢复与进度

每个任务的受保护目录为 `config/upgrade-state/<任务 ID>/`，保存数据库逻辑备份、各应用数据卷归档、安装配置和密钥归档、原执行器、原配置、摘要及恢复配方。权限 0700/0600；包含敏感数据，不得公开下载或提交仓库。默认保留这些产物；可按下方 U3 保留策略开启受保护清理。

切换前关闭所有应用数据写入者，保留 PostgreSQL 和只读 Web 容器。恢复先检查归档与摘要，再重建同一受管数据库并恢复应用卷，移除失败迁移新增的对象和文件，恢复配套旧配置与执行器。部署格式 `v1` 限定自动切换只修改 Compose、镜像环境配置和执行器；自动恢复这些改动，配置与密钥的完整归档另作人工灾难恢复依据。

独立进度通过同一管理入口的 `/upgrade-progress/<任务 ID>` 返回。随机只读凭据有效期为任务开始后的 4 小时，只保存在当前浏览器会话中；响应不含签名目录、环境变量、密码或恢复配方，Nginx 不记录该路径访问日志。后端重启期间继续读取宿主机记录；Web 重建期间可能短暂不可达，页面自动重连。凭据不能提交、取消或修改任务。

出现 `recovery_required` 时业务保持关闭，页面显示具体失败原因，独立进程只提供只读进度。管理员需在宿主机核验任务目录、备份和服务状态后恢复；不要删除冻结标记或升级记录来强制启动旧版本。修复操作需先停止对应独立升级服务，避免与其持有的安装锁冲突。

### 完整闭环目标

管理员选择明确版本并确认影响后，由独立 Upgrade Runner 继续执行；不能让会被升级脚本停止的部署执行器承担完整升级流程。

顺序：验证发布信息 → 提前下载固定摘要镜像 → 再次预检 → 阻止新会话和写任务 → 排空已有任务 → 备份数据库、应用数据、配置与密钥 → 校验备份 → 切换和迁移 → 更新执行器 → 验证入口和组件 → 开放业务。

任务状态、旧镜像、备份和阶段日志保存在应用容器外。升级与部署、恢复共享实例级互斥规则，重复点击不得重复迁移。浏览器关闭不取消已开始的升级；后端和 Web 重启后自动重连进度。单机入口切换允许短暂中断，不承诺零停机。

失败时按阶段处理：切换前保留原部署；未发生不兼容变化时恢复配套旧镜像和配置；已发生数据库或应用数据迁移时按已验证的恢复路径恢复配套数据。不能仅根据 schema 相同判断可回退，不能启动旧镜像直接访问可能已迁移的数据。

验收通过前保持业务写入关闭；开放写入后的回退作为独立恢复操作，明确数据影响。旧镜像始终保留，升级备份按 U3 保留规则处理。

首批目标为一键安装的 Linux amd64、Docker Compose、systemd 受管部署。Docker Desktop 容器化执行器及 PostgreSQL 大版本升级分别适配。检查端口及部署依赖，不管理防火墙或云安全组。

## U3 自动准备与维护窗口升级

在“系统运维 → 系统更新 → 自动准备与维护窗口”配置宿主机策略。先成功检查签名发布目录，再选择渠道及目录中已知的版本上限。保存策略需要当前管理员密码及已绑定 MFA 的动态口令，并使用 revision 防止覆盖另一管理员的修改。

| 模式 | 行为 |
| --- | --- |
| 关闭（默认） | 不创建自动升级任务；应用的定时检查设置独立生效 |
| 自动准备 | 检查布局、权限、空间及固定摘要镜像，下载所需镜像；不排空会话、不备份或切换版本，完成后显示“已准备” |
| 维护窗口升级 | 在授权窗口内开始完整 U2 流程；必须明确勾选允许停止会话，不能以自动准备授权代替停机授权 |

授权最长 30 天，指定 Beta 或稳定渠道和明确版本上限，不无限追随最新版本。默认不允许数据库结构版本变化；只有管理员单独允许后，目标 schema 变化才可进入备份和迁移流程。当前版本、最低来源版本、签名、布局和授权用户权限在执行时重新检查。应用数据库回退不会恢复旧自动授权，授权保存在宿主机 `config/upgrade-state/automation.json`。

维护窗口设置 IANA 时区、星期、开始时间和 15–240 分钟持续时间，支持跨午夜。夏令时不存在的开始时间跳过；重复时刻不会重复执行同一窗口。有效期输入按当前浏览器本地时间解释，窗口时间按所选 IANA 时区解释。每个授权版本的每个窗口至多预约一个任务；窗口截止约束开始停机的时间，已经开始的升级或恢复会继续完成，可能超出窗口。

宿主机每分钟调度，在有效时段内最多每 15 分钟访问固定签名更新源，使用宿主机 HTTPS 出站环境；这与后端页面的自动检查开关、代理环境和检查间隔分别生效。自动准备成功后，同一来源和目标不重复准备。准备完成不保证后续升级一定通过，正式执行会重新预检。

任务失败、已恢复原版本或需要人工恢复时暂停后续自动执行。修复原因后由管理员重新授权；授权到期不再启动新任务。活动任务期间拒绝修改策略，关闭浏览器不取消任务。下载、准备或排空前发现授权变化、权限失效或窗口到期时，不进入后续停机步骤。支持范围和失败恢复条件与 U2 一致，不管理防火墙或云安全组。

### 历史与产物保留

页面显示最近 50 个任务，包括手动升级、自动准备、窗口升级和失败恢复结果。可选产物保留天数为 30–365 天，`0` 表示不自动清理（默认）；此项独立于自动升级模式，即模式关闭但保留天数非零时仍会检查清理。

宿主机每天在部署与升级互斥锁内检查一次：仅处理超期的成功或已准备任务目录，保护当前任务、最近 3 个成功任务，以及所有失败、恢复和未完成任务。拒绝越界目录和符号链接，不删除 Docker 镜像、任务 JSON、发布序号和幂等记录。清理结果在策略卡片展示。升级备份不替代常规备份策略。

### 通知与 AI 查询

通知规则新增“自动准备完成”“自动升级成功”“自动升级失败”事件。必须选择指定人员，投递时再次核验接收人仍是有身份管理权限的平台管理员；渠道须自行配置。宿主机保留最近 30 条结果通知，跨任务和策略修改继续保留；后端恢复后将其去重写入现有通知队列，再按渠道规则投递。长期离线超过该容量时，以任务历史为完整依据；通知不参与恢复决策。

AI 助手新增管理员专用 `system_update_status` 只读工具，通过现有工具提议、批准、执行和审计流程查询缓存版本状态与升级进度。不会自动检查远端、安装版本、修改授权或请求管理员密码；需要操作时引导至系统更新页面。普通用户不能调用，输出移除独立进度凭据。

已有 beta0.10 需通过原升级脚本一次性升级到 beta0.11 或后续兼容版本，同步后端、宿主机执行器、冻结配置和进度入口后，才能使用上述功能。

## 发布索引维护

可信公钥位于 `backend/internal/platform/systemupdate/trust.json`。私钥不进仓库、镜像、日志或发布附件；发布维护者独立保管签名私钥。应用不信任从更新源下载的新公钥，新增或轮换信任根需单独管理。

首次建立签名密钥（在后端目录执行，目标文件必须不存在）：

```sh
go run ./cmd/puppeteer-release-index init --key /secure/release-private.json --public /secure/release-public.json
```

将公钥文件审阅后同步到应用信任根，再构建包含该公钥的版本。准备发布目录：

```sh
node scripts/prepare-update-index.mjs --version beta0.10 --min-source beta0.9 --sequence 1 --published-at 2026-11-16T08:07:08Z --output catalog.json
```

准备工具只包含指定版本。发布前核对真实发布日期、最低来源版本和兼容性；如需保留其他渠道或版本，将对应条目合并到目录。发布序号必须单调增加，索引有效期默认 30 天，更新或续期均使用新序号。

审阅目录后，在后端目录签名：

```sh
go run ./cmd/puppeteer-release-index sign --key /secure/release-private.json --input ../catalog.json --output ../deploy/production/updates/index.json
```

只有签名索引可供客户端消费。签名工具拒绝无效版本、错误镜像仓库、重复组件、错误产品标识和无效有效期。发布索引位于 main 分支的 deploy/production/updates/index.json，须在镜像及版本标签可访问后发布；更新或续期均需递增序号并重新签名。

## 验证要求

U1 覆盖数字版本比较、签名篡改、未知密钥、索引回退、同序号冲突、过期、渠道无版本、网络失败、并发检查、取消、持久化重启和缓存复核。接口回归覆盖未登录、非管理员、版本不在目录、设置版本冲突、任意脚本字段被拒绝，以及缺少独立升级器时不能通过预检。

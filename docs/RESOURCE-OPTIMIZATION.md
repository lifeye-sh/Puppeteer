# 资源优化：第一轮至第三轮

本文功能纳入 beta0.9 测试版，安装和升级说明见[发布说明](../deploy/production/beta0.9.md)。第二轮 10 小时复测尚在进行，不能视为完整稳定性验收。使用这些功能需要同批构建的 server、web、renderer 镜像和宿主机执行器。原部署未选择档位时保持原资源配置。

## 操作入口与流程

管理员进入 **平台配置 → 服务部署 → 资源档位**，选择轻量、标准或性能档，输入管理员密码及已绑定的动态口令，点击“预检并执行”。直达路径为 `/deployment-settings?section=resourceBudget`。这里与“业务策略 → 资源默认值”是两个独立入口。

预检检查标准单机 Compose、已接管组件、Docker CPU/内存、镜像能力和后台重任务。配置 MP4 时还检查 Docker 数据盘可用空间，至少保留 1280 MiB 用于一次转换及余量。执行器必须位于 Linux Docker 宿主机；远程 Docker 数据盘无法检查时明确失败。

执行前再次检查并暂停新重任务的领取，然后记录恢复配置，依次暂停服务、应用数据库预算、启动渲染器并检查临时卷、恢复应用、管理入口和图形组件。页面显示阶段与失败原因；应用短暂离线期间继续使用独立进度通道。完成时检查实际容器内存/CPU限制、健康状态和应用正在使用的档位。

**切换会重建容器并中断现有连接，应在维护窗口操作。** 不新增宿主端口，不修改防火墙或云安全组。已经关闭的图形或 MP4 组件保持关闭，原始录屏、密钥和业务数据卷保留。失败后恢复原 Compose 并启动原配置；若恢复本身失败，任务明确报告，不能把失败任务视为服务已恢复。

## 档位预算

单位为 MiB；容器内存是上限，并非预先分配或固定占用。轻量档宿主内存预检最低为 Docker 实际可见的 3584 MiB（3.5 GiB），不额外扣除预留；推荐目标仍为 4 GiB。标准和性能档保留标称容量 5% 的内核余量。3.5 GiB 整机稳定性尚待验收。CPU 数是 Docker 可用 CPU 数，不是购买套餐名称。

| 项目 | 轻量 light | 标准 standard | 性能 performance |
| --- | ---: | ---: | ---: |
| 宿主机目标 | 2 核 / 4 GiB | 4 核 / 8 GiB | 8 核 / 16 GiB |
| server 内存上限 | 768 | 1536 | 2048 |
| PostgreSQL 内存上限 | 512 | 1024 | 2048 |
| guacd 内存上限 | 512 | 1024 | 2048 |
| MP4 渲染器内存上限 | 1024 | 1536 | 2048 |
| web 内存上限 | 128 | 256 | 256 |
| 每个受管服务 CPU 上限 | 1 | 2 | 4 |
| Go 内存目标 GOMEMLIMIT | 512 | 1024 | 1536 |
| 后台重任务并发上限 | 1 | 1 | 2 |
| MP4 临时磁盘准入配额 | 2048 | 4096 | 8192 |

容器不额外使用 swap；CPU 上限可以共享宿主 CPU，不等同于独占核心。Go 内存目标是运行时软目标，不包含全部进程及其他容器内存。第一轮未调整 PostgreSQL 连接池与 SQL 参数；第三轮扩展见下文。自定义副本或 `deploy` 资源约束不自动覆盖，预检会给出原因。

这些是工程预算和后续压测目标，**不是已认证的最低生产配置或并发容量承诺**。特别是多路真实 Windows 桌面、高分辨率录屏和长时间混合负载，仍需针对实际使用量验收。

## MP4 流式处理与临时磁盘

上传直接分块写文件；归档按行校验，再顺序回放。网页图形回放按协议同步帧读取，不再在 Node 和浏览器中各保留整份录屏。原有 150 MiB 上传、100 MiB 解码数据、两小时录屏、256 MiB 输出、单任务编码及四个保留结果限制继续生效。单行最多 24 MiB；单个图形同步帧的输入保护为 32 MiB，超限任务失败，不导出被静默截断的视频。

选用资源档位后，执行器自动创建项目独占的 `mp4scratch` 命名卷，挂到渲染器的 `/var/lib/puppeteer-renderer`，缩小 `/tmp` tmpfs 到 128 MiB 供浏览器临时运行使用。命名卷位于 Docker 数据盘；若需要 SSD，应将 Docker 数据盘部署在 SSD 上。本轮页面不接受任意宿主机目录或外部存储卷。

每个新任务预留 768 MiB 的准入空间，同时检查现有文件占用、档位配额及文件系统剩余空间。**这是应用准入配额，不是文件系统硬配额，也不预先分配整块磁盘。** 转换仍可能因其他进程写满磁盘失败，页面会显示临时存储不足；原始录屏保留，可以处理空间后重试。

当前进程创建的任务按删除、取消和到期规则清理，完成转换后先删除上传中间文件。重启遗留文件保留并计入配额，不按目录名称自动递归删除。降档后遗留文件超过可用配额时，部署检查失败并恢复原档位。未选择档位的旧部署继续使用原 `/tmp` 模式，避免升级即迁移工作目录。

## 后台重任务调度

MP4 导出、备份创建/复制和它们的缓存/保留清理共用应用进程内的调度预算。领取任务前等待可用名额，等待期间任务保持排队，不占任务租约、不增加尝试次数。清理没有名额时推迟到下一轮，不删除额外数据。

轻量和标准档避免导出与备份同时竞争 CPU/磁盘；性能档允许两个重任务，渲染器自身仍一次只编码一个视频。未设置 `NT_RESOURCE_PROFILE` 的旧部署保留最多一个导出加一个备份的原行为。此调度适用于已接管的单应用单机部署，不是跨多个 API 副本的分布式限流器。

WAL/PITR、恢复和配置部署继续使用原有维护/互斥流程；本轮没有改变其恢复语义，也没有把全部定时业务任务归类为重任务。

## 安装、升级与兼容性

本轮不提高现有 schema，不改公开版本号与镜像摘要。服务端镜像声明 `io.puppeteer.resources=v1`，渲染器声明 `io.puppeteer.renderer.streaming=v1`。执行器在切换前检查所登记镜像；不匹配时拒绝执行。

升级脚本保留已选档位、组件关闭状态、临时卷和配额。启用过档位的部署在升级镜像拉取完成后、服务暂停之前检查目标能力，拒绝覆盖成缺少资源/流式能力的镜像。`--check` 只完成配置预检，不拉镜像；镜像能力在正式升级的拉取阶段检查。不要把当前 rc13 默认镜像手工覆盖到已开启新档位的开发部署。

## 第二轮：按需渲染、转换质量与空闲退避

当前仍为未发布的开发分支。管理员进入 **平台配置 → 服务部署 → MP4 渲染器**，开启组件后选择运行方式、默认质量，再点击“预检并执行”。默认保持常驻、均衡，不会在升级时自动替旧部署改档。修改运行方式或质量沿用组件部署流程：预检、保留队列、重建应用与渲染器、实际转换样例、恢复入口；失败回滚。**这次配置变更仍会中断连接，应安排维护窗口。**

### 按需运行

选择按需后，应用启用 `NT_MP4_ON_DEMAND=true`，受管渲染器使用 `restart: "no"`。无上传、无运行或保留结果，且空闲至少 5 分钟后，由宿主执行器停止渲染容器。维护检查每 30 秒执行一次；其他部署或维护占用执行器时顺延。旧结果会先按原到期规则清理，因此保留结果存在时不能保证 5 分钟内停止。

有转换任务时，后台先通过受认证的执行器 Unix socket 唤醒渲染器，通过健康检查后再领取任务。日常唤醒和休眠只操作 `mp4-renderer`，不拉取镜像、不重建应用或网页、不开放宿主端口。页面显示“待机”，有任务时显示唤醒或等待原因。执行器不可达、版本不匹配、部署忙碌或启动失败时，任务继续排队，自动重试，不占任务租约或增加转换尝试次数；用户仍可取消。

唤醒后有 5 分钟准备保护期，活跃任务每分钟续期；续期请求与数据库租约心跳独立。渲染器接到休眠请求时原子关闭新任务准入，并拒绝在上传、编码或保留结果时休眠。执行器重启后也从启动时刻起留出保护期，不因等待部署互斥而重新开始计时。普通 Docker 主机重启后按需渲染器保持停止，已启动的应用会在处理排队任务时唤醒它。宿主执行器必须已接管且正常运行。休眠检查失败会在组件说明和宿主执行器日志中显示原因并重试，异常退出与正常待机分开显示。

此模式减少空闲常驻开销，首个转换需要等待启动；它不降低活跃编码所需的内存上限。关闭 MP4 组件后不会因排队任务自动重新打开；已生成缓存仍按原授权提供下载。

### 新转换的默认质量

| 档位 | 终端与网页图形输出 | 原生 MP4 录屏兼容输出 |
| --- | --- | --- |
| 省资源 economy | 960 × 540，10 fps，CRF 28 | 960 × 540，保留原 10 fps 时间线，CRF 28 |
| 均衡 balanced（默认） | 1280 × 720，20 fps，CRF 25 | 1920 × 1080，保留原 10 fps 时间线，CRF 23 |
| 清晰 sharp | 1920 × 1080，20 fps，CRF 22 | 1920 × 1080，保留原 10 fps 时间线，CRF 20 |

配置落在渲染器 `NT_MP4_QUALITY`，所有新转换使用所选档位。只读原始录屏不改变；已有成功的 MP4 缓存不会自动重编码，切档不意味着现有下载已提高质量。画面等比缩放并补边；提升输出尺寸不能恢复原始录屏没有的细节。原生格式仅用于历史录屏兼容，不要求部署原生 RDP Worker，网页 RDP 继续使用图形组件。

### 空闲轮询

MP4 与备份后台队列无任务时按 1、2、4、8、15 秒逐级退避，本进程收到新建/重试请求时立即唤醒。外部进程入队或计划任务最多受 15 秒轮询间隔影响（不含排队及重任务占用）。数据库心跳与安全校验频率保持不变。部署页面空闲 15 秒刷新、执行中 2 秒刷新，独立进度通道在完成后停止；录屏导出执行中 2 秒、空闲 60 秒刷新。页面重新获得焦点及提交操作仍会刷新。

### 安装升级要求

新增能力标识：应用 `io.puppeteer.mp4.ondemand=v1`，渲染器 `io.puppeteer.renderer.lifecycle=v1`。使用同批 server、renderer、web 和宿主执行器。升级保留运行方式、质量和组件关闭状态；即使没有资源档位或渲染器已经关闭，脚本也会在停机前拒绝缺少已配置能力的目标镜像。`--check` 仍只检查配置，不拉取或验证未下载镜像。

第二轮回归覆盖三档实际 H.264 尺寸/帧率/末帧、原生录屏时间线、上传/结果占用时禁止休眠、执行器鉴权与部署互斥、唤醒失败队列保留和恢复。独立 Docker/systemd 验收入口：

```sh
python3 tests/deployd_docker_integration.py --renderer-demand --systemd --systemd-smoke \
  --server-image SERVER_IMAGE --renderer-image RENDERER_IMAGE --web-image WEB_IMAGE
```

该验收使用真实 5 分钟空闲期限，检查待机、唤醒后的样例转换及应用/网页容器 ID 不变；通常需要数分钟。测试创建独立项目并在结束后清理，不覆盖现有部署。长期混合负载、真实多路 Windows 桌面和远端渲染尚不在本轮验收结论内。


2026-11-15 第二轮最终验收：10 项渲染回归在 1 CPU / 1 GiB / 128 MiB tmpfs 约束下通过；50 项安装升级测试通过；真实 PostgreSQL 的队列失败保留、唤醒恢复及相关后端回归通过；前端生产构建、产物校验与菜单映射测试通过。独立 Docker/systemd 测试通过首次启用后的自然空闲待机、冷启动、样例转换、应用/网页容器连续运行及停用后拒绝唤醒。最终容量测试通过并发准入、取消、保留结果限制、运行控制鉴权、编码进程终止及磁盘写满后的恢复，容器 `OOMKilled=false`。这些结果不替代长期混合负载与实际生产容量验收。

本轮只完成开发与独立验收，未发布远程镜像、修改公开版本号或替换已有本地部署。


## 第三轮：数据库预算、任务空转与编辑器加载

仍为未发布的开发分支。重新执行资源档位部署后，除既有容器预算外，同时应用以下参数；应用和 PostgreSQL 会重建，操作前预检并在失败时恢复原配置。

| 参数 | 轻量 | 标准 | 性能 |
| --- | ---: | ---: | ---: |
| 应用连接池最大连接 | 8 | 12 | 20 |
| 应用连接池最小连接 | 1 | 1 | 2 |
| PostgreSQL max_connections | 40 | 60 | 100 |
| shared_buffers | 128 MiB | 256 MiB | 512 MiB |
| work_mem | 2 MiB | 4 MiB | 4 MiB |
| maintenance_work_mem | 32 MiB | 64 MiB | 128 MiB |

未设置档位的部署仍使用应用最大 10、最小 1 的原配置。连接余量留给管理、健康检查和维护任务。`work_mem` 可按执行节点与并行操作重复分配，表格不是数据库总内存硬上限；实际仍受容器预算约束。没有改变同步写入、归档或事务持久性设置。

首次接管若发现自定义数据库启动命令，或启动参数已包含本轮要管理的内存/连接项，预检会拒绝直接覆盖。其他规范的 `postgres -c name=value` 参数保留。WAL/PITR 开启、关闭及中途切换资源档位均保留当前数据库预算和原数据卷。完成时核对数据库 `current_setting`、应用连接池实际最大值、容器预算与健康状态。

应用镜像新增 `io.puppeteer.database.budget=v1`，受管 Compose 使用 `x-puppeteer-database-budget: 1` 标记。升级保留参数，并在停机前拒绝缺少此能力的应用镜像。已经使用新档位的开发环境也应升级匹配执行器，再重新应用档位；不需要手工编辑 PostgreSQL 配置文件。

### 后台任务与前端

SSH 命令任务和凭据轮换的两个工作进程在无任务时按 1、2、4、8、15 秒退避。手动触发与定时任务入队会唤醒本机工作进程；外部进程入队仍由最长 15 秒的空闲轮询发现。执行中的心跳、取消与权限撤销检查不降频，不改变远端副作用失败后的恢复语义。

定时调度原先每秒尝试最多 10 次，即使第一条查询已没有到期任务仍继续查询；现在没有到期任务就结束本轮，有任务时仍最多处理 10 条。租约恢复与计划触发检查仍每秒执行，避免把恢复延迟混入空闲优化。

文件管理页按需导入 Monaco 编辑器，只有打开编辑器时才加载其代码和语言 Worker。关闭时卸载编辑器视图，未保存内容继续由父级文件状态保存。本次生产构建的文件管理页面 JS 从约 1322 kB 降到约 38 kB，编辑器成为独立异步块；这不是整个站点体积减少，首次编辑仍需要下载编辑器。

### 性能采样与查询计划

新增只读脚本 `scripts/performance-baseline.py`：按明确的 Compose 项目采集 CPU、容器内存、Block I/O、网络、PID、健康状态、重启计数及 OOM 状态。可增加 HTTP GET 探测，输出成功请求的 P95 延迟和错误数。不会读取容器环境、健康检查输出或凭据，不修改部署；容器内存采用 Docker stats 口径，不等同于宿主整机占用。

```sh
python3 scripts/performance-baseline.py --project puppeteer --scenario idle \
  --seconds 120 --interval 5 --output ./measurements/before-idle.json

# 在安排好并持续运行相同工作负载后采集长时间数据；此脚本本身不产生负载。
python3 scripts/performance-baseline.py --project puppeteer --scenario mixed \
  --seconds 86400 --interval 10 --output ./measurements/mixed-24h.json
```

### 图形数据与录屏

批处理计算指令长度时不再生成一份临时编码字符串；发送时直接追加编码到连接内复用缓冲。缓冲超过 64 KiB 后不长期保留，单条指令仍受原协议上限约束。批次的 64 KiB / 128 条 / 8 ms 限制及 sync 边界不变。数据库事务完成后才发送给浏览器，仍在录制失败时中断会话，不丢帧、不异步跳过审计、不改变配额与完整性规则。

### 新转换等待资源恢复

领取 MP4 任务之前，应用先检查本地缓存磁盘、系统可用内存以及常见 Docker cgroup v1/v2 的应用容器内存。缓存剩余低于 512 MiB、系统可用内存低于 256 MiB 或总量的 5%、应用容器剩余低于限额的 10% 时暂缓领取；指标不可读也显示原因并保留任务。非标准 cgroup 挂载布局可能只能检查系统内存，不能将此机制当作 OOM 保证。

渲染器提供需鉴权的 `/runtime/admission` 内部预检，检查正在上传/转换、保留结果数量、临时磁盘与配额及可用内存；可用内存低于 256 MiB 时暂缓新任务。实际提交时再次检查，预检不预占容量。旧渲染器返回 404 时兼容原提交流程，完整预检需要升级匹配渲染器。

资源不足时页面显示等待原因，继续按现有最长 15 秒空闲退避重试，不创建任务租约、不增加转换尝试次数。预检之后的资源竞争若导致 429、507 或明确的内存不足响应，也会保留同一任务并归还本次尝试次数。取消、权限和原始录屏完整性校验保持有效；指标恢复后仍需等已有任务释放容量。已有交互会话不由准入机制中止，正在转换的任务仍可能因真实磁盘/内存耗尽失败。

## 10 小时结果与复测修正（2026-11-16）

首轮完成 600 轮负载、1200 次 MP4 导出及 10 次加密备份，无 OOM、重启或健康失败；合计内存中位 358.69 MiB，内核高水位 993.86 MiB。应用每小时 Go 堆低位 4.91→16.25 MiB，需继续定位；555 次进程采样中有 10 次观察到单个僵尸进程，前 9 次在下一次采样消失，最后一次缺少后续确认，因此当时未签收无泄漏结论。

后续隔离诊断确认测试辅助函数的父级 `testing.T.Cleanup` 会持有已经关闭的 WebSocket 及读写缓冲，SSH 测试目标也保留历史连接引用。600 次连接对照中，旧模式在 GC 后多保留 6,228,184 字节，逐轮显式关闭后为 13,216 字节；堆快照将旧模式主要保留定位到 WebSocket/bufio 与测试 cleanup。长测改用调用方管理连接生命周期，SSH 测试连接结束即从活动集合移除。诊断的显式 GC 只用于归因，持续测试仍按自然 GC 采样；这不等于证明所有业务内存增长均已消除。

另复现取消转换时并发两次 `browser.close()` 的收尾竞态：后一次可能在第一次完成进程回收前返回。渲染器现在共享并等待同一个关闭 Promise，同时处理浏览器启动期间取消。25 次正常转换加 5 次取消的高频进程观察通过，最终僵尸为 0；完整 14 项渲染回归、5 项 SSH 集成回归、5 项报告测试及资源恢复测试通过。180 秒混合复测通过，最终空闲探针只剩 Tini 与 Node、僵尸为 0。

取消修复已更新本地渲染镜像并健康就绪。第二轮 10 小时复测使用修正后的负载程序及进程探针：按 PID/启动时间复查退出中的进程、结束时补充空闲检查，并对较小但连续多小时的堆增长告警。正式版本和镜像发布仍等待复测结论，不覆盖首轮原始证据。

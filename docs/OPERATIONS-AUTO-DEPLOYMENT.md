# 专项运维自动部署（P2）

rc13：数据库 schema 110、能力版本 90，配套公共镜像已发布。使用匹配的前端、server 镜像和安装/升级脚本。本文描述 rc13 功能；远程服务器仍需执行升级。

## 使用入口

管理员进入「平台配置 → 服务部署」，选择「Agent 更新仓库」「WAL / PITR」或「网页入口限制」。填写参数、管理员密码及已绑定的动态口令，点击「预检并执行」。页面显示期望、配置应用、依赖、实际结果四个维度及任务阶段；API 重启期间使用独立进度通道，刷新后可继续追踪。

预检失败不改变活动部署。实际执行会再次核对部署版本与应用权限。任务与其他代理/组件部署互斥；失败自动恢复原配置，停用失败继续完成停用。恢复不依赖应用 API 在线。只管理已接管的单机 Docker Compose；不修改防火墙、云安全组、域名解析，也不将本机验证解释为公网可达。

安装和升级自动登记兼容能力，不自动启用三项功能。自定义镜像、外部卷或未接管的 Nginx 策略会显示原因。无需手工添加 Compose 文件、映射端口或安装定时任务。

## Agent 更新仓库

填写 HTTPS 签名仓库地址，以及从独立可信渠道取得并核验的 `1.root.json`（公开元数据，不能填签名私钥）。例如地址为 `https://updates.example.com/agents/stable`，内容使用该发布者提供的真实可信根，不能使用示例或从同一不可信下载地址直接建立信任。

执行器校验 HTTPS、最多 16 代根轮换链、签名、有效期、元数据版本及可选摘要/长度、目标 SHA-256 和发布身份。已发布的目标序号与根版本不得回退，相同序号不能替换目标内容。签名私钥不下载、不上传；仅导出根元数据、targets/snapshot/timestamp 和 `targets/nt-agent-linux-amd64`。

验证完成后只读挂载公开目录，自动配置现有 Nginx 的 `/agent-updates/`。通过本机 HTTPS 下载核对实际目标摘要。Agent 仍按其已登记的信任根和更新策略验证下载；部署仓库不等于自动升级所有 Agent。后续版本由管理员再次提交发布，元数据过期显示失败。停用后入口返回失败，历史发布和防回退记录保留。

## WAL 归档与数据库恢复

支持标准内部 PostgreSQL 18 命名数据卷部署。应用须在线、未处于恢复隔离状态，且仍使用已接管的 `postgres/puppeteer` 数据库。自定义 PostgreSQL 参数、镜像、外部归档挂载不自动覆盖。

开启前检查数据库版本、健康及空间，至少需要数据库总大小三倍加 512 MiB 的空闲空间。启用按以下顺序执行，并显示各阶段：

1. 生成独立加密密钥，按仓库内固定配方自动构建 PG18 + pgBackRest 镜像；构建需要镜像及包仓库网络。
2. 保留原 PostgreSQL 数据卷，仅添加专用归档卷与只读密钥；重建 PostgreSQL 容器，连接会短暂中断。
3. 初始化 stanza，检查归档，创建第一份完整加密备份。
4. 创建命名恢复点并归档，在无网络、无公开端口的临时容器和独立卷中恢复。等待重放到恢复点并完成提升，确认应用数据库基本结构可读，然后清理演练资源。
5. 全部通过才显示「数据库恢复链路已验证」，接管每周完整备份、每日差异备份、每五分钟归档检查；保留两份完整备份及其依赖链。

后台任务与部署操作共用互斥锁。应用恢复隔离、数据库切换或应用离线时暂停并显示原因，恢复条件满足后自动重试。执行器重启清理仅带本项目演练标签和受限名称的临时资源，不删除源数据库或归档卷。

停用恢复原 PostgreSQL 镜像及启动参数，停止归档和后台调度，保留原数据、历史归档及 `config/deployd-state/wal_cipher_pass`。失败恢复也不删除这些数据。受保护的失败诊断在 `config/deployd-state/wal-last-error.log`，不会通过页面返回命令输出或密钥。

本功能证明本地数据库备份及命名恢复点链路，不替代异地副本、应用文件、离线密钥备份或完整业务恢复验收。不会自动对正在使用的生产库执行破坏性恢复。已有专项恢复流程继续使用隔离恢复、验证和显式切换。

## 网页入口访问限制

先在「业务策略 → 客户端 IP」确认可信代理范围及来源提取方式。标准 Nginx 会覆盖来源头为实际对端地址；页面显示服务端识别的 IP，预检拒绝未验证来源或自定义不兼容头转发规则。

例如当前 IP 是 `203.0.113.42`，填写 `203.0.113.42/32`；需要内网再添加实际可信网段，例如 `10.20.0.0/16`。采用规范 CIDR，最多 64 项；必须包含当前管理员来源。不要把示例 IP 当作实际 IP。部署校验 Nginx 语法、启动健康和本机 HTTPS 管理文档；保留容器回环恢复入口。停用撤销限制并验证入口。部署已有外层反向代理时，范围对应标准 Nginx 看到的对端，不能据此区分该代理后面的最终用户。

入口策略与 Agent 仓库复用现有 HTTPS 服务，无新增宿主端口。策略启用仍须使用平台登录和授权。

## 升级与状态

接管信息保存在受保护的 `compose-managed.json` 扩展字段中。升级保留专项启停状态、WAL 原镜像恢复配方、归档卷/密钥、仓库发布记录和策略挂载。普通版本升级不更换数据库镜像或重置这些状态。配置发生变化时旧专项证据标记过期，需重新预检并执行；实际容器异常不能继续显示通过。

保留整个安装配置目录及数据库、应用文件的匹配备份。不要手工删除 deployd 状态以绕过仓库防回退或恢复保护。

## 验证范围

`tests/operations_docker_integration.py` 使用随机、一次性的 Docker 项目验证 Nginx 放行/拒绝、签名仓库实际下载与停用、WAL 首份备份、命名恢复点演练、停用保留数据/密钥、后台调度隔离、执行中断恢复和演练残留清理。只给专用测试运行器 Docker socket，应用容器不接收 socket。

另有 Go 竞态与静态检查、实际代理连接及内部执行接口集成测试、安装/升级命令替身回归、前端生产构建与浏览器交互验收。测试夹具不代表已完成远程生产安装、升级或发布；共享盘 AppArmor 的宿主内核强制访问验收仍按 P1 发布门槛执行。

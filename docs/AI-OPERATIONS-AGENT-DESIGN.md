# Puppeteer 智能运维 Agent 设计方案

日期：2026-11-16。代码基线：beta0.10。

状态：设计方案，待开发。本文保存已讨论的功能范围与分阶段计划，不代表 beta0.10 已具备这些新增能力。阶段 A、B、C 独立于此前部署自动化的 P0、P1、P2。

2026-11-17 状态补充：当前 beta0.11 增加管理员专用的系统更新状态只读工具，可在全局对话中经批准执行；该工具不执行升级，也不自动回传结果给模型。下述完整 Agent 阶段仍待开发，原 beta0.10 基线分析作为设计背景保留。

## 1. 产品目标

将现有 AI 助手升级为 Puppeteer 智能运维 Agent。用户描述目标后，Agent 自主查找资源、制定方案、检查条件、调用系统功能、验证结果，并返回有依据的报告。

核心体验：能自行完成的连续完成，缺少必要信息时才询问；需要审批时展示具体操作，批准后自动继续。

覆盖全部业务模块，执行权限始终继承当前用户。通过统一能力清单记录每项操作的接入状态、权限要求、执行条件、验证方式和测试状态；未接入的能力明确说明，不能声称已完成。

## 2. 现有基础与差距

现有实现具备模型调用、对话与用量、工具提案、参数审批、执行审计、取消和超时控制。工具包括资产元数据、会话命令审计、SSH 命令及文件读写。

当前主要限制：

- 依赖用户选定的资产或已连接的 SSH 会话；缺少自主查找资源和任务级连接管理。
- 工具结果保留在平台，需要用户手动选取并发送给模型，尚未形成自动分析和继续执行的闭环。
- 缺少跨资产、多步骤及跨业务模块的持久化任务编排。
- 页面以聊天和单次工具审批为主，尚未提供完整任务计划、批量进度和最终结果验证。

| 功能领域 | 目标能力 | 用户示例 |
| --- | --- | --- |

| 运行状态与诊断 | 采集 CPU、内存、磁盘、进程、服务、连接及日志，分析异常 | 检查 work 为什么变慢了 |

| 网站 | 创建网站资产、配置代理、发布、检查证书与可达性 | 把内部管理网站接入平台 |

| 文件与运维任务 | 检索文件、生成变更预览、发布文件、运行受控命令 | 修改配置并验证服务是否恢复 |
| 备份与恢复 | 查询策略、执行备份、校验、恢复预检和恢复流程编排 | 立即备份并确认备份可恢复 |
| 审计与报表 | 汇总操作、定位失败、关联会话和工单、输出报告 | 昨天谁访问过生产数据库 |
| 系统配置 | 检查和调整邮件、身份源、证书、通知及业务策略 | 检查邮件发送失败的原因 |

## 4. 工作模式

| 模式 | 行为 |
| --- | --- |
| 只给方案 | 查询必要信息，给出步骤、影响和预期结果，不执行变更 |
| 协助执行 | 自动查询和预检，展示具体变更，确认后连续执行 |
| 自动处理 | 在管理员设置、用户权限及本次任务范围内完成操作，超出范围才暂停 |

避免逐条命令反复确认。用户可一次批准完整任务，例如“检查生产组的运行状态”，授权范围包括指定资产、期限、采集项目及资源预算。

自动模式不增加用户权限，不能绕过审批、为自己扩大授权，或将“查询状态”自行升级为“重启服务”。

## 5. 典型任务流程

### 5.1 资产运行状态检查

用户输入：

> 检查 work 的运行情况，看看有没有资源不足或异常服务。

1. 定位资产：在用户可访问的资产中查找 work，读取协议、系统信息和可用连接方式；同名且无法确定时才询问。
2. 预检条件：检查资产权限、AI 执行策略、凭据引用、网络路径和命令执行能力。失败时明确显示无法连接、无执行权限或缺少采集通道。
3. 制定采集计划：优先使用经过验证的 Linux、Windows 诊断模板，再根据实际结果补充检查。普通运行状态检查限定在选定资产，不自动扩大到整个网段。
4. 建立任务连接并采集：无需用户预先打开终端；复用已有连接和审计能力建立受控连接，限制超时、并发和输出量。
5. 分析与追加检查：磁盘使用率过高时检查限定范围内的目录占用；服务异常时读取限定时间范围的日志。扩大采集范围或修复前重新判断授权。
6. 返回结果：展示指标、采集时间、异常证据、影响判断、建议和关联执行记录，区分已确认问题、可能原因及未能检查的项目。

网页 RDP 连接能力不等同于后台执行 PowerShell 的能力。Windows 自动巡检需要单独支持并验证命令采集通道；缺少通道时展示可用信息和接入方法，不能把远程桌面连接成功视为完成系统巡检。

### 5.2 创建资产并授权

用户提供资产信息和目标人员后，Agent 查找可复用分组及凭据引用，检查字段、连接条件和操作权限，展示待创建资产及授权关系。按策略确认后创建资产，再调用批量授权能力，回读资产和有效授权并报告结果。

无法推断的必要字段通过表单或简短问题补齐；密码等秘密通过安全表单填写，不进入模型上下文。资产创建成功而授权失败时，明确报告部分完成，不重复创建资产。

### 5.3 审批辅助

Agent 整理申请对象、资源、期限、申请理由及相关策略，向有审批权限的用户提供判断依据。审批决定沿用现有业务接口、授权和职责分离规则；模型不能代替独立审批人批准自己的申请。

### 5.4 开启远程访问

区分打开资产的网页远程会话、部署平台协议入口、修改目标主机远程服务三类操作。根据上下文确定含义，存在实质歧义时询问。

平台协议入口复用现有部署执行器，自动完成预检、发布和实际服务验证，沿用端口占用与部署依赖检查，不新增防火墙或云安全组管理范围。目标主机服务变更需要独立的命令通道和相应授权。

## 6. 核心架构

| 能力 | 开发内容 |
| --- | --- |
| 统一工具目录 | 为各模块定义类型化工具，包含参数、权限、风险、预检、执行、验证、幂等和可回退性 |
| 任务编排器 | 将目标拆成步骤，处理依赖、分支、批量执行、等待审批和追加诊断 |
| 任务授权 | 保存允许的资产、操作、期限及预算；每一步执行时重新检查当前权限 |
| 结果回传 | 将脱敏、限量、带来源的结果交给模型分析，支持继续调用工具 |
| 持久化任务 | 页面关闭或网络断开后仍可跟踪；重启后恢复状态并避免重复执行 |
| 结果验证 | 业务修改后回读状态，远程操作后核验结果，不能以请求发送成功作为完成依据 |

业务工具复用现有应用服务和权限校验，不另建资产、授权或部署逻辑。批量授权、SQL 工单、部署执行器、备份任务作为对应工具的执行基础。

远程主机 Agent 提供连接或采集能力，AI Agent 理解需求并编排任务；不能假设现有连接 Agent 已支持任意命令执行。

实施时需明确任务与步骤的状态转换、幂等标识、授权有效期及事件契约。最低状态包括计划中、预检中、等待确认、等待审批、执行中、验证中、成功、部分成功、失败、取消及结果未知。原始操作结果与模型总结分开保存，并可关联到业务审计证据。

## 7. 执行与审批规则

| 操作 | 建议默认处理 |
| --- | --- |
| 查询授权内资产、状态、任务记录 | 自动执行 |
| 已批准诊断模板、限定范围的运行检查 | 在任务授权范围内自动执行 |
| 创建资产、批量授权、修改配置 | 自动完成预检和变更预览，按策略确认后执行 |
| 审核访问申请 | 整理依据，由具备审批权限的用户确认决定，保留职责分离规则 |
| 重启、删除、恢复覆盖、扩大访问范围 | 展示目标、影响及恢复条件，执行对应确认或审批 |
| 秘密输入与导出 | 使用专用安全表单或下载流程，不进入模型上下文 |

命令风险由服务端工具定义、模板及策略判断，不能接受模型自行声明安全。

授权绑定实际目标、参数和版本；目标或参数变化后重新检查。运行期间撤权时停止后续操作，并按现有业务能力处理正在执行的步骤。远程结果未知时先核查，不自动重放写操作。

跨资产部分失败时逐项报告。回退仅用于有明确补偿能力的操作，不承诺任意命令和跨系统修改都能自动回滚。

任务中止应停止后续步骤并尝试终止运行任务；已经发生的修改、无法终止的操作和需要核查的结果分别说明。

## 8. 数据与模型上下文

现有工具结果不自动发送给模型。新增闭环执行需要显式的数据回传策略，按用户、资产、工具及模型配置允许范围。

- 凭据、令牌、私钥和恢复密钥始终排除，通过引用交给业务执行器使用。
- 日志、文件和命令输出按字段、大小、时间范围及用途筛选；原始结果留在平台，模型接收允许的摘要或片段。
- 外部日志、资产备注、文件内容和工具结果均作为不可信数据，不能成为扩大授权或改变执行策略的指令。
- 分析结论带采集时间及证据来源，区分事实、推断和未知状态。
- 限制模型轮次、任务时长、并发、输出大小和费用；触及预算时明确结束或等待用户调整，不能无界循环。

## 10. 开发阶段与完成标准

| 阶段 | 开发范围 | 完成验收标准 |
| --- | --- | --- |
| A 自主巡检闭环 | 工具目录、任务编排、任务授权、资产搜索、受控连接、Linux 诊断模板、结果回传、进度、取消及审计 | 一句话完成指定资产巡检，无需先开终端或复制结果；权限变化、断线、超时、重启均有明确处理 |
| B 跨模块操作 | 创建资产、批量授权、申请与审批辅助、网页远程会话、数据库与网站代理部署、数据库只读诊断和 SQL 工单 | 一句话创建资产并授权；开启代理自动预检、发布、验证；审批遵循原有权限与规则 |
| C 完整覆盖与持续运维 | 其余配置、文件、备份恢复、证书、通知、Windows 采集、批量运维、定时巡检、告警触发、模板复用 | 能力清单逐项验收；计划任务使用明确委托授权；异常自动处理受范围和期限约束 |

阶段 A 必须交付完整可用体验，不能以聊天界面、命令生成按钮或单次工具调用代替完成。

首批端到端验收任务：

1. 检查这台 Linux 服务器的运行情况并给出报告。
2. 比较这五台服务器的资源占用，找出异常。
3. 检查失败的原因，能在已授权诊断范围内继续排查就继续。

每阶段验收需覆盖正常流程和故障流程：越权访问被拒绝、执行前撤权生效、审批参数改变失效、重试不重复写入、断线后结果可追踪、未知结果不自动重放、取消后状态准确，以及报告与实际业务结果一致。

真实 Windows 采集须在具有有效采集通道的 Windows 资产上验证；不能使用 Linux 夹具或 RDP 连通测试替代。备份可恢复性需以适用的校验或隔离恢复结果为依据，不能仅凭备份任务成功判断。

## 11. 性能与部署原则

沿用既有性能优化方向，复用 Go 服务、PostgreSQL 任务记录和部署执行器，按需加载工具定义。限制任务并发、模型轮次和结果体积，避免为每次对话启动额外容器。

后台任务不依赖浏览器持续在线。定时或告警任务使用明确、可撤销、有期限的委托授权，不能将用户浏览器登录会话当成长期授权来源。

上线前应完成对应工具的能力登记、权限和审计验证、真实执行验证、故障恢复及资源占用检查。按阶段开放能力，未完成的工具不出现在可执行清单中。

## 12. 实施顺序

先完成阶段 A 的自主巡检闭环，再将同一套任务机制扩展到阶段 B 的授权、审批和部署操作，最后完成阶段 C 的完整覆盖与持续运维。

本方案保存后不改变现有 AI 开关、用户权限、部署状态或已发布镜像。具体接口、数据迁移和默认执行限额在各阶段开发时确定并纳入验收记录。
